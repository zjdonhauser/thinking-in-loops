The Shift

Prompt Engineering → Loop Engineering

Prompt engineering optimizes a single human → agent turn. Loop engineering optimizes the system that drives the agent — and you build it once.

Before · Prompt engineering
You type each prompt

One turn at a time. Every instance starts from scratch. The lessons live in your head and evaporate between tasks.

After · Loop engineering
You design the loop; it prompts the agent

Your job moves up a level: orchestrator + high-level decision-maker. The loop finds work, iterates, and self-checks.

⚖️ Loop design is harder than prompt design — but you do it once and it pays back across every run. More up-front structure, far less manual repetition.
The Compounding Part

What Makes a Loop Self-Improving

A plain script automates the steps. A self-improving loop gets better every time it runs — that's the difference that matters.

The ratchet
A retrospective is baked in

The final step asks: what was wrong / missing this run? what edge case generalizes? — and folds the answers back into the loop immediately, while the friction is fresh.

Memory
It captures the non-obvious

The hard-won lessons that normally evaporate between tasks get written into the steps — so they're never relearned.

Tooling
It bundles its own templates

Repeated boilerplate becomes templates the next run reuses instead of rebuilding from zero.

Grounding
It grows from real cases

Each run appends a worked example, so the loop generalizes from reality, not theory.

📈 Net effect: run N+1 is cheaper and more correct than run N. By-hand work has no such ratchet.
When To Use It

Reach for a Loop When…

✓ Reach for a loop when
  • The work is a known, repeatable shape — onboarding a new X, a migration, an audit, a review sweep.
  • You'll do it more than a couple of times — enough for the up-front design to pay back.
  • The output is verifiable — tests, a benchmark, a printed-total oracle — so the loop can self-check without you in the seat.
✗ Don't, when
  • The work is genuinely one-off and novel.
  • There's no checkable success signal for the loop to close on.
  • The thinking itself is the deliverable and doesn't repeat.
🎯 The sweet spot: a shape you've already done by hand a few times, with a real-world oracle that can tell the loop when it's right.

The Skill Process

Inside the Loop · The 12 Phases

Worked in order, one checkable step at a time. Each links to a reference file with the concrete commands — and each run sharpens the steps for the next. Hover any phase for what it does.

0Investigate real docsⓘ
Pull real examples, read their stored OCR, and catalog the variance — before designing anything. The one rule that matters most.
1Design the schemaⓘ
Faithful + document-native: transcribe what's printed, add only light mechanical derivation. Flat arrays + grouping keys — no array-in-array.
2Prompt blocksⓘ
Compose the system prompt from reusable, doc-type-agnostic blocks. Make a new block only when it's cohesive — never fragment arbitrarily.
3Migrationⓘ
One migration: flip the registry row to enabled, insert the prompt sections + the versioned schema. Insert a new version, never mutate.
4Post-processorⓘ
A pure function that re-nests the LLM's flat arrays into the stored wire shape and derives aggregates. Unit-tested with literal in/out.
5Benchmarkⓘ
Ground-truth from real docs via the fast local harness; verify against the real doc; report adjusted scores only. The accuracy gate.
6Classificationⓘ
Confirm a fresh doc routes to the new type. Old docs read as their pre-existing type (stale labels) — only tune hints if a fresh doc misroutes.
7Scope & follow-upsⓘ
State clearly what's in this PR vs deferred (e.g. the consumer-side ingest). File follow-up tickets instead of contorting DI now.
8Consumer handoff specⓘ
A skim-first doc for the PR reviewer + downstream team: real examples, the DI-vs-consumer scope boundary, and the field mapping.
9Verifyⓘ
Build + tests + the scorer over the regression set, then one final end-to-end run through the real pipeline as a sanity check.
10Staging verificationⓘ
The real end-to-end on a prod replica: fresh classification, source attribution, push behavior, and accuracy across the wider corpus.
11Refine this skill ⟳ⓘ
Retrospective — fold what was wrong / missing back into the skill now, and grow the worked-example set. The self-improvement step.
🧠 The skill encodes the thinking (Phase 0 — investigate before you design), not just the mechanics. Get the thinking right and the rest is downstream.

The Playbook

How to Build One

01  Do it by hand first

You can't abstract a shape you haven't felt. Dogfood a few times, then distill.

02  Name the phases

The repeatable sequence, one checkable step at a time.

03  Encode the thinking

Front-load the high-leverage judgment, not just the mechanics. "Investigate the real inputs first."

04  Bake in the retrospective

Make it the final phase — this is what makes it self-improving, not a static checklist.

05  Bundle & grow

Templates for boilerplate, worked examples from each run, pre-flight checks that encode past failures.

06  Keep the spine general

Task-shaped, not output-shaped — so it transfers to adjacent work with override instructions.

07 Let it run; you orchestrate. Design the loop, make the high-level calls, and let the loop drive the agent.
Takeaways

Start Thinking in Loops

01  Loop, don't hand-prompt

When work is a known shape you'll repeat, design the system that prompts the agent — not each turn.

02  Self-improving = the ratchet

A baked-in retrospective makes run N+1 cheaper and more correct than run N. That's the whole game.

03  Verifiable or bust

A benchmark / test / oracle is what lets the loop self-check and run without you in the seat.

04  Keep the spine general

One well-shaped loop covers a family of adjacent tasks with override instructions.
